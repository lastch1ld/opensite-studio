# Security & architecture audit — 2026-08-28

The audit [roadmap.md](roadmap.md) deferred until the whole roadmap was
built. Phases 0–4 are complete, so this is that pass.

Scope and method: a read of the authentication/authorization surface
(every `app/api/**/route.ts`), the two upload paths, outbound server-side
fetches, the rendering paths that inject HTML, secret handling, and the
public/unauthenticated endpoints — then the architecture as built against
[architecture.md](architecture.md). Static reading plus targeted greps; no
Postgres was available, so nothing here was confirmed by running the app.
Findings marked **fixed** were fixed in the same pass and are noted with
the mechanism, not just the change.

## Findings

### 1. Stored XSS via the media upload path — **fixed**

`mimeType` was stored from `file.type`, which is client-supplied and
trivially forged, with no allowlist; the extension came from the original
filename. `app/api/media/[siteId]/[file]` then served the bytes back from
the app's own origin with that stored `Content-Type` and no hardening
headers.

So a file uploaded as `text/html` was served as a document on the
dashboard's own origin. Reaching the upload needs EDITOR on some site —
but signup is open and a new user is OWNER of their own site, so this was
self-service, not privileged. SVG had the same shape without the forgery
step, since an SVG opened as a top-level document runs its script.

Fixed in `lib/media.ts`: an explicit type allowlist, the extension derived
from the validated type and never from the filename, and a 10MB cap. The
serve route additionally sends `X-Content-Type-Options: nosniff` and a
`default-src 'none'; sandbox` CSP, so anything stored before this — the
allowlist doesn't retroactively clean the volume — can't execute either.

### 2. Unauthenticated, unbounded writes to the media volume — **fixed**

`app/api/forms/submit` is public by design, and it wrote every uploaded
file straight to disk. App Router route handlers have no default body-size
limit, so filling the volume cost one request; the per-IP rate limit
(10/minute) bounded the request count, not the bytes.

The same `validateUpload` now runs before anything touches disk.

### 3. Form-submission attachments were unreachable — **fixed**

Not a security hole, a real bug the security read turned up: submitted
files are deliberately given no `Media` row, and the public media route
only serves files that have one. Every uploaded attachment therefore
resolved to a 404 in the Submissions panel.

Now served by `app/api/sites/[siteId]/form-attachments/[file]`, behind an
OWNER/EDITOR check, as an `attachment` download with a generic type — the
right exposure for a file a stranger uploaded, which the public media
route would have been wrong for even if it had worked.

### 4. `embed` block's sandbox was not a sandbox — **fixed**

The block rendered `sandbox="allow-scripts allow-same-origin"`. Those two
flags together are equivalent to no sandbox: a `srcDoc` frame keeps the
embedding origin, so its scripts can reach `parent.document`. In the
editor canvas the embedding origin is the dashboard, which makes any
embed authored by an EDITOR a script running as whoever opens the page.

Now `allow-scripts` only, so the frame runs in an opaque origin — which is
what the inspector label already claimed.

### 5. SSRF in the form webhook — **fixed**

`onSubmit.action === "webhook"` called bare `fetch()` on an
editor-supplied URL. This server sits inside a self-hoster's network, so
that reaches `localhost`, private ranges, and cloud metadata endpoints.
`lib/safeFetch.ts` already existed for exactly this and the newsletter
webhook already used it; the form webhook had been missed. Now uses
`safePostJson`.

## Open, not fixed here

- ~~**Visitor tokens never expire.**~~ Fixed 2026-09-03. The signed body
  now carries an `exp` and `lib/visitorToken.ts` rejects anything past it,
  including a correctly signed token that has no `exp` at all — otherwise
  every token minted before the fix would have kept its forever-validity.
  Visitors holding one sign in again once.
- **Rate limiting is in-process.** `lib/rateLimit.ts` says so itself. Fine
  for the single-container deploy `deployment.md` describes; the moment
  there are two instances the limit is per-instance.
- **`x-forwarded-for` trust.** `app/api/forms/submit` takes the last entry
  as the proxy-appended one. Correct for the Caddy setup in this repo,
  wrong for a proxy that replaces rather than appends — worth an env
  toggle if other topologies get supported.
- **Media stored before finding 1 was fixed** is not re-validated. A
  self-hoster with existing uploads keeps whatever is on the volume; the
  serve-side headers are what protect them.

## Architecture

The load-bearing invariants hold:

- **One shared block-rendering codepath.** `BlockRenderer` really is the
  single renderer for the editor canvas, `/preview`, and the public site.
  The divergences are deliberate and narrow: the public renderer emits
  media-query CSS while the editor re-renders per selected breakpoint, and
  (as of the Phase G fix) the editor re-points the full-bleed breakout at
  its canvas frame via `--osw-bleed-width`. Both are commented at the
  point of difference.
- **JSON block tree as the source of truth**, `draftContent` →
  `publishedContent` on publish, public renderer reading only the latter.
  Intact.
- **Single Next.js app.** Intact.

Drift worth correcting rather than defending:

- `architecture.md` still describes `components/ui/` as the app chrome's
  design-system primitives. In reality the chrome's vocabulary is the
  `.chrome-*` layer in `app/globals.css`, and `components/shared/` holds
  one cross-surface component (`ConditionEditor`).
- `AGENTS.md` rule 5 still reads "No `packages/` workspace split". That
  was right when written and is now stale: `packages/block-sdk` and
  `packages/plugin-api` exist, which is exactly the "second consumer"
  exception `architecture.md` allows for. Corrected in AGENTS.md.
